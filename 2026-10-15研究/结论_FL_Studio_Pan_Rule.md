# FL Studio Mixer Pan Rule —— 逆向结论

**结论日期**：2026-10-15
**被测软件**：FL Studio 20.8.3.2304（`FLEngine_x64.dll`，2021-03-25，未加壳 x64 PE，镜像基址 0x400000）

---

## 1. 结论（TL;DR）

FL Studio 混音台（Mixer track）的 Pan 对**立体声**信号的规则如下。记 pan `p ∈ [-1, 1]`，
`θ = (p + 1)·π/4`（`p = -1` → θ=0，中心 → θ=π/4，`p = +1` → θ=π/2），并令

```
A = √2 · cos θ        # 记为"左/中"增益，A ∈ [0, √2]
B = √2 · sin θ        # 记为"右"增益，   B ∈ [0, √2]
```

则：

| | 左声道输出 | 右声道输出 |
|---|---|---|
| **p ≤ 0**（向左） | `L' = A · [((1+B)/2)·L + ((1−B)/2)·R]` | `R' = B · R` |
| **p ≥ 0**（向右） | `L' = A · L` | `R' = B · [((1+A)/2)·R + ((1−A)/2)·L]` |

等价的 2×2 传递矩阵 `[L', R']ᵀ = M(p)·[L, R]ᵀ`：

```
p ≤ 0 :  M = [[ A(1+B)/2 ,  A(1−B)/2 ],
              [    0     ,      B    ]]

p ≥ 0 :  M = [[     A     ,      0    ],
              [ B(1−A)/2 ,  B(1+A)/2 ]]
```

两边在 `p = 0` 处一致且都等于单位矩阵 `I`（中心＝原样直通，实测 `L'` 精确等于 1.0000000000）。

用 `φ = p·π/4 ∈ [−π/4, π/4]` 也可以写成（更贴近"代码里可能的样子"）：

```
p ≤ 0 :  gLL = (cosφ − sinφ + cos2φ)/2 ,  gLR = (cosφ − sinφ − cos2φ)/2
         gRL = 0                        ,  gRR = cosφ + sinφ
p ≥ 0 :  gLL = cosφ − sinφ              ,  gLR = 0
         gRL = (cosφ + sinφ − cos2φ)/2 ,  gRR = (cosφ + sinφ + cos2φ)/2
```

### 1.1 这个规则的性质

- **单声道输入**（`L = R = s`）：两个表达式都退化为 `(L', R') = s·√2·(cos θ, sin θ)`，
  即**严格等功率**（`L'² + R'² = 2s²` 恒定），硬极点处增益为 `√2 = +3.01 dB`。
  这与官方手册 "Circular panning … a maximum of 3 dB can be added" 完全一致。
- **100% 极右**（`p = +1`，θ=π/2）：`L' = 0`，`R' = (L+R)/√2` —— 正是官方手册说的
  "a 100% pan is the mono-sum of the Left and Right channels"。
  极左对称：`L' = (L+R)/√2`，`R' = 0`。
- **硬声像输入 + 同向扫描会出现 >1 的增益**：输入 `L=1, R=0` 时，
  `L'(p≤0) = A(1+B)/2 = (√2·cosθ + sin2θ)/2`，其极大值在
  `sinθ = (√34 − √2)/8 = 0.55209229…`（θ = 33.5107°，**p = −0.25531841**）处取到

  ```
      max L' = 1.049898788408…   (+0.4229 dB)
  ```

  实测峰值 `1.04989886283875`，吻合到 **7.4e-8**（即 1 个 float32 ULP 量级）。
  该增益 >1 的区间为 `p ∈ [−0.519251, 0]`。
- 矩阵关于"左右镜像"自洽：`M(p)` 与 `M(−p)` 互为 `L↔R` 交换（`J·M(−p)·J`）。

## 2. 这张表是怎么解出来的

数据：`2024-09-19测试/test_pan_2024-09-19.wav`（32-bit float，48 kHz，384750 帧）。
输入 `DC偏移100%_左声道.wav` 为恒定 `L = 1.0, R = 0.0`（8.000 s），
播放时在播放列表里用自动化控制器把 **Mixer 轨道 Pan 从 −100% 线性推到 +100%**
（项目 Panning law = Circular）。

因为 `R ≡ 0`，输出直接给出矩阵第一列：`L'(p) = gLL(p)`，`R'(p) = gRL(p)`。

关键识别步骤：

1. `R'(p)` 在 `p ≤ 0` 时**恒为精确 0**，且在**正好第 192001 帧**开始非零
   → 自动化确实在 t=4 s 过中心，`p(t)` 是线性斜坡，且 `p=0` 处有硬边界。
2. 令 `u = (p+1)/2`，发现 `R'(p)` 与 `L'(p)` 的两组组合量恰好是纯三角函数：
   - `gLL + gRL = √2·cos(45°(p+1))`
   - `gLL − gRL = cos(90°·|p|)`
   由此解出 `gLL`、`gRL`（`p ≤ 0` 分支），再用镜像对称补出 `p ≥ 0` 分支。
3. 对 `p ≥ 0` 分支，`gLL` 实测恰好等于 `cosφ − sinφ`（逐点吻合到 2e-5）。

## 3. 验证

### 3.1 全帧验证（对照原始渲染，384000 帧）

| 用哪个 θ(t) | L 通道最大误差 | L 最大相对误差 | R 通道最大误差 |
|---|---|---|---|
| 名义线性斜坡 `p = 2i/383999 − 1` | 6.46e-05 | 6.2e-04 | 5.38e-05 |
| **从数据反解出的真实 θ(i)** | **9.45e-08** | **1.0e-07** | 8.41e-06 |

即：**给定真实 θ，规则与渲染结果吻合到 float32 精度**。剩下的 6.5e-05 全部来自
自动化时间轴自身的抖动（见第 4 节），与 Pan 规则无关。

### 3.2 独立交叉验证

- **同定律、另一份渲染**：`2023-06-21测试/test_pan.wav` 峰值比
  `L/R = 1.484771`，模型给 `1.484781`；公共缩放因子 0.7070587 ≈ 1/√2
  （该次测试源电平低 3 dB，16-bit 量化解释了剩余 4e-5 偏差）。
- **单声道输入渲染**：`2023-06-21测试/test_sinewave.wav`，
  按 `R'/L' = tan θ` 反推的 θ 范围为 `[0.05004, 1.52076]`，
  与线性斜坡范围 `[0.05211, 1.52099]` 吻合 → 单声道等功率分支成立。

### 3.3 与官方文档比对

| 官方文档说法 | 本规则 |
|---|---|
| Circular 下"最多可增加 3 dB" | 单声道时硬极点 = √2 = **+3.01 dB** ✅ |
| Mixer pan"把一侧混入另一侧" | `p≤0` 时 R 漏进 L；`p≥0` 时 L 漏进 R ✅ |
| "100% pan 就是 L+R 的单声道和" | 极右 `R'=(L+R)/√2`，极左 `L'=(L+R)/√2` ✅ |
| 手册图：中心比极值低 3 dB（或反之） | 单声道：中心 (1,1)、极值 (√2,0)，`|L|+|R|` 中心为 2、极值为 √2 → 中心比极值**高** 3 dB（与"音频片段默认设置下音量在极值处被加上"这一句对应）✅ |
| 文档未给出任何闭式公式 | —— 本报告补上 |

**文档查不到的部分**：官方手册、本地语言包（`Panning law` → 声像法则 / 圆形 / 三角形）、
`WhatsNew.rtf` 全版本历史（只有一条：11.0.3 "Updated triangle panning law not to sound
louder"）、以及 19 个 Image-Line 论坛帖，**均未给出任何 gL/gR 闭式**；也没有任何地方
提到立体声与单声道规则不同、或存在 >1 的中间增益。

### 3.4 等功率性质的独立实测

`test_sinewave.wav` 假定为单声道输入（`L = R = s`）。此时本规则预测
`L'² + R'² = 2s²`，**与 pan 无关**。逐 10 ms 窗口取包络（480 样本、共 801 窗，可取 779 窗）：

```
peakL² + peakR² :  min 0.999999   max 1.001971   mean 1.001219   std 5.80e-04
相对离散度 1.97e-03  ← 正好是 16-bit 量化量级
⇒ 隐含源幅度 s = 0.707538 ≈ 1/√2，输出峰值 √2·s = 1.0000
```

即 `A² + B² = 2` 这个"√2 量级"（也就是 +3.01 dB）在**另一份独立渲染**上被直接实测确认，
不是靠单一数据集拟合出来的。

### 3.5 证伪实验：另一条规则被明确拒绝

同一套拟合办法用在 `2023-06-21测试/test_dc.wav`（同样 384750 帧的 16-bit 直流渲染）上
**会被否决**：

| | test_dc 实测 | Circular 规则预测 | 无驼峰的规则预测 |
|---|---|---|---|
| `L'max / R'max` | **1.414388** | 1.484781 | 1.414214 |
| 左半区 `L'` | 恒为 0.380402（`dL ≡ 0`） | 0.7071·a → 1.0499·a → a | 恒为 a |
| 拟合残差（L 通道 rms） | — | **0.1107（拒绝）** | 吻合 |

也就是说 `test_dc.wav` 是**另一条 pan 规则**下的渲染：左半区 `L'` 恒定、`R' ≡ 0`，
`L'/R'` 峰值比恰为 `√2`。这个形状与官方手册描述的 **Triangular**（"no level compensation"）
一致，也可能来自通道机架（Sampler）自己的 pan。这里不作断言，但它提供了一个**负对照**：
本报告的模型是可证伪的，且在正确数据上吻合到 float32 精度、在另一条规则上被判否。

### 3.6 逐条结论的证据来源

| 结论 | 实验 | 官方文档 | 论坛 | 源代码 |
|---|---|---|---|---|
| 中心＝原样直通（`L'` 精确 1.0） | ✅ | ✅ Circular 图 | ✖ | ✖ |
| 极右 `= (L+R)/√2`、另一侧 0 | ✅ | ✅ "100% pan is the mono-sum" | ✖ | ✖ |
| 单声道等功率、硬极点 +3.01 dB | ✅ (3.4) | ✅ "max 3 dB can be added" | ✖ | ✖ |
| 左/右半区公式不同、`p=0` 有折点 | ✅ | ✖ 未涉及 | ✖ | ✖ |
| 立体声交叉项 `(1±B)/2`、`(1±A)/2` | ✅ | ✖ 未涉及 | ✖ | ✖ |
| 驼峰 `1.0498988 @ p=−0.255318` | ✅ + 解析解 | ⚠️ 文档法则均**不可能**产生 >1 | ✖ | ✖ |
| 排除"通道 pan = 混音台 pan" | ✅ | ✅ channelrack 页 "sent to the plugin" | ✖ | ✖ |

**坦率结论：闭式形式（尤其曲线中段、驼峰、立体声交叉项）目前只有实验支撑**；
文档只能交叉验证端点行为与单声道情形；论坛层面不存在任何公式可供核对；
**源代码层面没有取得**（见第 5 节），这是唯一的缺口。

## 4. 残留：自动化时间轴的微小波纹（≈ −84 dB）

把 θ 从数据里逐帧反解后，它与"完全线性"之间存在一个**平滑**的周期波纹：

- 幅度：θ 上约 ±4.1e-05 rad（换算到增益约 ±5.9e-05，约 **−84 dB**）
- 周期：约 **750 帧 @48 kHz = 15.625 ms**（384000 帧共 512 个周期）
- 相位只依赖帧序号、与 pan 位置无关（左半区与右半区同相位）

这解释了为什么此前用正弦/多项式拟合永远得不到"完美结论"：**规则本身是精确的，
不完美的部分在自动化时间轴**，而不是 Pan 规则。`拟合.py` 里
`P = after_l² + after_r²` 不是常数，也正是因为同一原因。

## 5. 还没做成的部分（逆向代码）

`rea` MCP 的原生 provider 只有 Ghidra（Hopper 仅 macOS），而**本机 Ghidra provider 未配置**
（缺 `GHIDRA_INSTALL_DIR`，且本机只有 JDK 17.0.5，它要求 JDK 21+），
因此**没能用反编译器读出 FL 的 Pan 代码**。

用 `capstone` / `pefile` 自建的静态扫描结论：

- 已定位字符串：`PanLawLabel`、`PanLawSelect`、`Circular`、`Triangular`、`Panning law`、
  `Center panned signal`、`Get/Set track pan`、`Get/Set channel pan`。
- 对它们做 RIP 相对（disp32）与绝对（VA 字面量）双重引用扫描，**全库 0 命中**。
  这与 FL 的**本地化字符串池**机制一致（字符串按 ID 从语言包 `.mo` 取，代码不直接引用地址），
  所以这条路走不通。
- 也没有找到任何 float32 预计算 pan 增益表（`1/√2 = 0.70710677` 在整个 52 MB 里 0 次精确出现）。

因此**代码级确认尚未完成**；但实测（第 3.1、3.2 节）已经在 float32 精度上把规则钉死了。
